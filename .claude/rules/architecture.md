# Архитектура проекта

Модифицированная **MVVM**-архитектура (Model-View-ViewModel) с модульной
структурой. Проект — упрощённая CRM: вход, сводка, клиенты, товары,
заказы. Бэкенда нет, все данные — на моках (см. раздел "Данные и
моки").

Эти правила описывают целевую структуру проекта — именно ей нужно
следовать при написании кода. Проект в начале пути: часть описанного
ещё не создана и не настроена (см. раздел "Ещё не настроено" в
`CLAUDE.md`).

## Корень проекта

```
./
├── .env.example        # шаблон переменных окружения, коммитится в git
├── .env                # реальные значения, НЕ коммитится (см. .gitignore)
├── .gitignore
├── eslint.config.ts
├── .prettierignore
├── .prettierrc
├── package.json
├── tsconfig.json
├── vite.config.ts
└── src/
    └── ...              # см. дерево ниже
```

- `.env.example` — эталонный список переменных окружения с
  плейсхолдер-значениями, всегда актуальный и закоммиченный в git; при
  добавлении новой переменной окружения в проект нужно добавлять её
  ключ и сюда (без реального значения).
- `.env` — реальные значения для локальной разработки, в `.gitignore`,
  в репозитории отсутствует. Полностью в ведении пользователя — Claude
  Code не создаёт, не читает и не редактирует этот файл самостоятельно
  ни при каких обстоятельствах без явного разрешения пользователя
  каждый раз заново (см. `safety-rules.md`).
- `eslint.config.ts`, `.prettierrc`, `.prettierignore` — конфигурация
  линтера и форматирования проекта.
- `package.json`, `tsconfig.json`, `vite.config.ts` — стандартные
  конфиги проекта; здесь же настраивается алиас `@/` (в tsconfig через
  `paths`, в `vite.config.ts` через `resolve.alias`).

- Каждая папка компонента/экрана содержит сам `.tsx`-файл и, если нужны
  стили, файл `.styles.ts` рядом (не в отдельной подпапке).

## Модули проекта

| Модуль      | Что делает                 | Маршруты                                 |
| ----------- | -------------------------- | ---------------------------------------- |
| `auth`      | вход в систему             | `/login`                                 |
| `dashboard` | сводка и статистика        | `/`                                      |
| `customers` | клиенты                    | `/customers`, `/customers/:customerId`   |
| `products`  | товары                     | `/products`, `/products/:productId`      |
| `orders`    | заказы                     | `/orders`, `/orders/:orderId`            |

- В `auth` только вход: регистрации и восстановления пароля нет.
- Корзина, оплата и доставка в проект не входят.
- Новый модуль или маршрут сверх этого списка — только после
  согласования с пользователем.

## Файловый роутинг в `app/`

Структура папок внутри `app/` определяет маршруты, а не ручная
конфигурация роутов в одном файле. Соглашения — как в Next.js App
Router:

- `page.tsx` — страница маршрута. Экспортирует `Page`.
- `layout.tsx` — обёртка для всех вложенных маршрутов папки.
  Экспортирует `Layout` и рендерит вложенный маршрут внутри себя.
- Папка в круглых скобках (`(auth)`, `(protected)`) — группа маршрутов:
  объединяет роуты по доступу и общему layout, в URL не попадает.
- Папка в квадратных скобках (`[customerId]`) — динамический сегмент
  (`:customerId`).
- Обычная папка — сегмент URL с тем же именем.

Роутинг строится строго на `react-router-dom`, без сторонних
роутер-библиотек и плагинов. `app/index.tsx` находит файлы `page.tsx` и
`layout.tsx` через `import.meta.glob` и собирает из них дерево
маршрутов. Точный API `react-router-dom` сверяется с документацией
установленной версии (см. `package-docs-verification.md`).

`page.tsx` — тонкая обёртка: импортирует экран из
`@/modules/<moduleName>/public` и рендерит его. Логики, запросов и
стилей в `page.tsx` нет.

## Ключевые принципы

- **Инкапсуляция модуля.** Другие модули и `app` импортируют из модуля
  ТОЛЬКО через `modules/<moduleName>/public/index.ts`. Прямые импорты из
  `model/`, `viewModel/`, `view/` другого модуля запрещены. Например,
  `dashboard` берёт данные клиентов и заказов только из того, что
  `customers` и `orders` экспортируют через `public/index.ts`.
- **model** — данные и контракты модуля: типы, константы, схемы
  валидации, запросы, моки. Файлы плоские, без подпапок.
- **viewModel** — связывает model и view: хуки, бизнес-логика,
  состояние экрана. Не содержит JSX. Жёсткого паттерна именования
  файлов здесь нет — называются по смыслу (`useLoginForm.ts`,
  `useCustomersList.ts` и т.п.).
- **view** — презентационный слой: компоненты и экраны. Ничего не знает
  о запросах и данных напрямую, только через viewModel.

## Правила слоёв MVVM (кто на кого может ссылаться)

Направление зависимостей строго одностороннее:
`view → viewModel → model`. Обратные и «диагональные» зависимости
запрещены.

- **model не знает о `viewModel` и `view`.** В `model/` не должно быть
  импортов из `viewModel/` или `view/` того же модуля, а также никаких
  React-хуков и JSX. `model` — чистые данные, типы, запросы и, при
  необходимости, стор (например zustand) — без UI-логики.
- **viewModel не содержит JSX и не импортирует ничего из `view/`.**
  `viewModel/` может использовать `model/` того же модуля и общие вещи
  из `core/` (хуки, сторы, утилиты). Обратной зависимости (`model` →
  `viewModel`) быть не должно.
- **view использует только `viewModel`, напрямую не обращается к
  `model`.** Компоненты и экраны в `view/` не должны напрямую вызывать
  `<module>Api.ts` или читать `<module>Store.ts` — только через хуки из
  `viewModel/`. Исключение — простые статические типы/константы из
  `model/`, если это оправдано (например тип пропсов, совпадающий с
  типом из `model`), но сама логика и данные — только через
  `viewModel`.
- **Между модулями — только через `public/index.ts`.** Один модуль не
  может напрямую использовать `viewModel` или `model` другого модуля в
  обход его `public/index.ts`.
- **`core` не знает о `modules/`.** Общая инфраструктура не должна
  импортировать что-либо из конкретных модулей — зависимость идёт
  только в одну сторону: `modules/* → core`, никогда наоборот.
  Исключений нет.
- **`app` — только композиция.** В `app/` не должно быть бизнес-логики:
  только сборка модулей, роутинг и обвязка (провайдеры, layout). Вся
  логика — внутри соответствующих модулей.

## Назначение подпапок `core/`

Это окончательный набор подпапок `core/` — ничего сверх него не
добавлять самостоятельно; если понадобится что-то, что явно не
укладывается ни в одну из существующих подпапок, нужно спросить
пользователя, куда это отнести, а не создавать новую подпапку по своей
инициативе.

- `api/` — общая обвязка запросов. Пока бэкенда нет — `mockRequest.ts`,
  помощник, который имитирует асинхронный запрос (см. "Данные и моки").
- `assets/` — статические файлы, которые импортируются в код:
  изображения, иконки, шрифты.
- `constants/` — общие константы приложения (`colors.ts`, `fonts.ts` и
  т.д.).
- `declarations/` — глобальные `.d.ts` файлы (декларации типов для
  сторонних модулей/ассетов).
- `hooks/` — переиспользуемые хуки, не привязанные к конкретному
  модулю.
- `types/` — общие типы приложения, включая `AppThemeType`,
  `StyleArgumentType`, `StyleConfigType` для системы стилизации (см.
  ниже).
- `layouts/` — обёртки-раскладки страниц (например `AppLayout` с
  навигацией для защищённых маршрутов).
- `providers/` — контекст-провайдеры (например `ThemeProviderManager`,
  оборачивающий `EmotionThemeProvider` — см. раздел про стилизацию).
- `locales/` — интернационализация: `translations/en.json`,
  `translations/ru.json` и т.д., `index.ts` — точка инициализации i18n.
  Заводится, только когда в проекте появится перевод интерфейса.
- `routes/` — общая логика роутинга: `PrivateRoute.tsx` (см.
  "Авторизация и сессия").
- `ui/` — переиспользуемые UI-компоненты дизайн-системы, каждый в
  своей папке по тому же принципу, что и `view/components/` модулей
  (`Button/Button.tsx` + `Button.styles.ts`, именованный экспорт
  `export const Button`). Данные получают только через пропсы, своей
  viewModel у них нет.
- `stores/` — глобальные zustand-сторы, не привязанные к одному
  модулю, а нужные приложению целиком: `sessionStore.ts` (сессия
  пользователя, с `persist`-мидлварой) и `themeStore.ts` (тема, с
  `persist`-мидлварой). Разграничение с `<module>Store.ts`: если
  состояние используется несколькими модулями или относится к
  приложению в целом — сюда; если состояние принадлежит только одному
  модулю — в `model/<module>Store.ts` этого модуля.
- `styles/` — глобальные стили и инфраструктура стилизации:
  `global.css` плюс `stylesConfiguratorHook.ts` (см. ниже).
- `utils/` — общие вспомогательные функции, в том числе `jwt.ts`
  (сборка и разбор токена).

## Данные и моки

Бэкенда нет, генерации типов из OpenAPI нет.

- Типы запросов и ответов пишутся вручную в `model/types.ts` модуля по
  правилу `<Module>Request` / `<Module>Response` (см.
  `code-conventions.md`).
- Mock-данные модуля лежат в `model/mocks.ts`.
- `model/<module>Api.ts` — асинхронные функции, которые отдают данные
  из `mocks.ts` через `mockRequest` из `core/api/`. Сигнатуры такие же,
  какими они были бы при настоящем бэкенде: принимают `Request`,
  возвращают `Promise<Response>`.
- `viewModel/` и `view/` не импортируют `mocks.ts` напрямую и не знают,
  что бэкенда нет. При появлении бэкенда меняется только содержимое
  `<module>Api.ts` и `core/api/`.

## Авторизация и сессия

Сессия относится к приложению в целом и живёт в `core/`. Модуль `auth`
отвечает только за экран и форму входа.

- **Вход.** `modules/auth/model/authApi.ts` — mock-вход: проверяет
  учётные данные по `mocks.ts` и возвращает `AuthResponse` с
  пользователем и токеном в формате JWT (три части через точку:
  заголовок, полезная нагрузка, подпись). В полезной нагрузке есть срок
  действия `exp`. Токен собирается функцией из `core/utils/jwt.ts`;
  подпись ненастоящая — это имитация формата, а не защита.
- **Хранение.** `core/stores/sessionStore.ts` хранит токен и
  пользователя, сохраняет их между перезагрузками через `persist` и
  предоставляет действия входа в сессию и `logout`. Хук из
  `modules/auth/viewModel/` после успешного входа кладёт результат в
  `sessionStore`.
- **Проверка.** `core/routes/PrivateRoute.tsx` используется в
  `app/(protected)/layout.tsx`. Он читает токен из `sessionStore` и
  проверяет срок действия `exp` через `core/utils/jwt.ts`. Если токена
  нет — редирект на `/login`. Если срок истёк — `logout` и редирект на
  `/login`.
- **Разбор токена.** Полезная нагрузка токена после разбора имеет тип
  `unknown` и проверяется zod-схемой; `as` не используется (см.
  `code-conventions.md`).

## Стилизация

Стилизация построена на `@emotion/react` по единому паттерну, других
подходов (styled-components, CSS-модули, Tailwind и т.п.) в проекте не
использовать:

- Каждый компонент/экран, которому нужны стили, имеет рядом файл
  `<Name>.styles.ts`, который экспортирует функцию `styles(theme, ...)`,
  возвращающую `StyleConfigType`, и хук `useStyles`, созданный через
  `stylesConfiguratorHook(styles)` из
  `core/styles/stylesConfiguratorHook.ts`.
- `stylesConfiguratorHook` — единая фабрика хуков стилей: берёт тему
  через `useTheme()` из `@emotion/react` и мемоизирует результат
  `styles(theme, ...args)` через `useMemo`.
- Типы для системы стилей (`AppThemeType`, `StyleArgumentType`,
  `StyleConfigType`, `AppColorsType`, `ThemeModeType`) лежат в
  `core/types`, названы с суффиксом `Type` согласно `code-conventions.md`.

### Тема: светлая и тёмная

- Режим темы (`ThemeModeType`: `light` / `dark`) хранится в
  `core/stores/themeStore.ts` с `persist`-мидлварой zustand — выбор
  пользователя сохраняется между перезагрузками.
- Цвета обеих тем лежат в `core/constants/colors.ts`.
- `core/providers/ThemeProviderManager.tsx` читает режим из
  `themeStore`, собирает объект темы и передаёт его в
  `EmotionThemeProvider`. Подключается в корневом `app/layout.tsx`.
- Компоненты не читают `themeStore` ради цветов — цвета приходят
  только через `useStyles`. `themeStore` нужен напрямую только
  переключателю темы.

## Формы и валидация

- Работа с формами — строго через `react-hook-form`, других библиотек
  форм в проекте не использовать.
- Валидация форм — строго через `zod`. Схема валидации формы лежит в
  `model/schema.ts` модуля и подключается в `viewModel/` через
  `zodResolver(schema)` из `@hookform/resolvers/zod`. Сама форма
  (`useForm`, обработчики) — в `viewModel/`, компонент формы в `view/`
  — только рендерит поля и вызывает переданные из viewModel обработчики,
  не содержит логики валидации.
