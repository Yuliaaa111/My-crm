# Правила поведения агента (безопасность и процесс)

Это правила поведения Claude Code в этом репозитории, а не про
архитектуру кода (для этого см. `architecture.md`,
`naming-conventions.md`, `code-conventions.md`, `imports-exports.md`).

Часть требований ниже дополнительно подкреплена технически через
`permissions` в `.claude/settings.json` (`ask`/`deny`) — это настоящее
принуждение, которое не даст обойти запрет независимо от того, следует
ли модель инструкциям из этого файла. Здесь же описано намеренное
поведение: зачем это нужно и как себя вести в пограничных случаях,
которые `permissions` не может выразить технически.

## Удаление

Любое удаление — файлов, папок, веток, записей в БД, ресурсов через API
и т.п. — требует отдельного явного подтверждения от пользователя перед
выполнением, каждый раз. Массовые операции (`rm -rf`, удаление
нескольких файлов разом, drop таблицы и т.п.) — то же самое, плюс явно
показать пользователю, что именно будет удалено, перед тем как
спросить подтверждение.

## `.env` и секреты

Файл `.env` (и любые другие файлы с реальными секретами/ключами)
строго под запретом без явного разрешения пользователя: не читать, не
открывать и не логировать содержимое без разрешения, каждый раз заново.
`.env` в проект добавляет и поддерживает сам пользователь вручную;
Claude Code не создаёт и не изменяет `.env` самостоятельно — только
`.env.example` (публичный шаблон без реальных значений) можно читать и
редактировать свободно.

## Конфликт правил и существующего кода

Если в рамках задачи выясняется, что существующий код нарушает
зафиксированные правила (архитектуру, нейминг, использует `interface`
вместо `type` и т.п.) — не проводить рефакторинг этого кода "заодно"
молча. Нужно сообщить пользователю о конфликте и спросить, стоит ли
провести минимальный рефакторинг конфликтующего участка в рамках
текущей задачи, прежде чем его трогать. Новый код в рамках самой задачи
в любом случае пишется строго по правилам, независимо от решения по
рефакторингу окружающего легаси-кода.

## План перед началом задачи

Перед тем как начать писать или менять код в рамках новой
задачи/диалога, нужно сначала кратко изложить план действий и оформить
его как файл-чек-лист: `.claude/plans/<task-name>.md`, где
`<task-name>` — короткое осмысленное имя задачи (kebab-case). Каждый
пункт плана — отдельный чекбокс `- [ ] <шаг>`.

- Дождаться подтверждения/продолжения от пользователя перед тем как
  приступать к реализации.
- По ходу выполнения — отмечать выполненные пункты как `- [x]` прямо в
  этом файле по мере продвижения, а не одним разом в конце.
- Когда все пункты плана выполнены и пользователь подтвердил, что
  результат его устраивает — удалить файл плана (само удаление — тоже
  с подтверждением, по правилу про удаление выше).
- Исключение — тривиальные точечные правки в рамках уже согласованного
  и не устаревшего плана в этом же диалоге: для них новый файл плана не
  нужен.

## Git: коммиты, пуши, PR

- **Запрещено самостоятельно коммитить.** Никаких `git add`,
  `git commit` без явного отдельного запроса пользователя именно на это
  действие в текущем сообщении. Подготовка изменений в рабочей
  директории — можно, коммит — только по прямой просьбе.
- **Запрещено самостоятельно пушить.** Никаких `git push` ни в какую
  ветку без явного отдельного запроса пользователя.
- **Запрещено самостоятельно открывать pull request.** `gh pr create` и
  т.п. — только по прямой просьбе пользователя, каждый раз заново.
- **Запрещено коммитить или пушить напрямую в `main`/`master`.** Даже
  если пользователь попросил закоммитить/запушить, но не указал ветку —
  нельзя делать это в `main`/`master`; нужно уточнить целевую ветку или
  использовать текущую рабочую (feature-ветку), но не главную.

## Прочие необратимые/влияющие на общий репозиторий действия

Список выше не исчерпывающий: по умолчанию любое потенциально
необратимое или влияющее на общий репозиторий/продакшн действие
(удаление, force push, изменение истории git, деплой, отправка
писем/уведомлений и т.п.) требует явного отдельного подтверждения, даже
если формально не перечислено здесь.

## Проверка перед завершением задачи

После того как все пункты плана из `.claude/plans/<task-name>.md`
выполнены, но до того как сообщить пользователю о завершении:

1. Если в проекте есть тесты, относящиеся к затронутому коду —
   запустить их и, если нужно по задаче, написать/дополнить тесты для
   нового или изменённого кода перед тем как считать задачу готовой.
2. Если тестов по этой части кода нет — самостоятельно перепроверить
   сделанное: перечитать изменённые файлы и свериться с
   `architecture.md`, `naming-conventions.md`, `code-conventions.md`
   (границы слоёв MVVM, нейминг, отсутствие `interface` вместо `type`,
   отсутствие мусорных комментариев и т.п.), и при найденных
   несоответствиях исправить их самостоятельно в рамках той же задачи.
3. Только после этого — сообщить пользователю, что задача выполнена,
   кратко перечислить, что сделано, и спросить, всё ли устраивает и
   можно ли удалить файл плана `.claude/plans/<task-name>.md`.
   - Если пользователь подтверждает — удалить файл плана.
   - Если пользователь говорит, что что-то не так или нужно доработать
     — не удалять план, а обновить его (добавить/поправить пункты по
     комментариям пользователя) и продолжить работу над задачей.
