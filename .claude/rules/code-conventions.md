# Кодовые конвенции

Правила про стиль кода внутри файлов (не про структуру папок — см.
`architecture.md` и `naming-conventions.md`).

## Функции

- Преимущественно стрелочные функции. Исключение — где стрелочная
  функция технически не подходит (нужен свой `this`, или объявление
  до использования через hoisting).

  ```ts
  // ✅
  const calculateTotalPrice = (items: CartItemType[]): number => { ... };

  // ❌
  function calculateTotalPrice(items) { ... }
  ```

- Название функции — глагол/глагольная конструкция, отражающая
  действие: `fetchUserProfile`, `calculateTotalPrice`, `formatDate`.
  Булевые функции/предикаты — с `is`/`has`/`should`/`can`:
  `isValidEmail`, `hasPermission`, `canEditPost`. Обработчики событий —
  с префиксом `handle`: `handleSubmit`, `handleInputChange`. Асинхронные
  функции по возможности называть так, чтобы было ясно, что это
  запрос/асинхронное действие (`fetchUsers`, `loadOrderDetails`), без
  искусственного суффикса `Async`, если и так понятно из контекста.
- Никаких сокращений и бессмысленных имён.

  ```ts
  // ✅
  const fetchUserProfile = async (userId: string): Promise<UserProfileType> => { ... };

  // ❌
  const doStuff = async (id) => { ... };
  const tmpFn = () => { ... };
  ```

- Один уровень абстракции на функцию: если функция разрослась и делает
  несколько разных вещей — выносить подшаги в отдельные именованные
  функции, а не оставлять как один длинный блок с
  комментариями-разделителями.

## Типы

- Используем только `type`. `interface` в проекте не используется
  вообще — ни для пропсов, ни для моделей данных, ни для API-ответов, ни
  для чего-либо ещё. **Правило абсолютное, без исключений** — даже если
  пользователь в моменте явно попросит написать через `interface`,
  нужно написать через `type` и коротко напомнить, что в проекте
  `interface` принципиально не используется; выполнять `interface`-вариант
  не нужно без отдельного явного пересмотра пользователем самого
  правила (не разовой просьбы по одной задаче).

  ```ts
  // ✅
  type UserType = { id: string; name: string };

  // ❌
  interface IUser {
    id: string;
    name: string;
  }
  ```

- Именование типов — PascalCase, без префиксов `T`/`I`.

  ```ts
  // ✅ UserType
  // ❌ IUser, TUser
  ```

- **`any` запрещён** (и `as any`). Если тип неизвестен заранее —
  `unknown` с последующей проверкой, либо дженерики, либо конкретный
  union/`type`. Если типизация не выводится сама и компилятор ругается
  без явного указания типа — писать явную типизацию через дженерики
  (`useState<User | null>(null)`, `array.map<ResultType>(...)`); если
  TypeScript и так корректно выводит тип — не дублировать аннотацией без
  необходимости.
- **`satisfies` не использовать.** Вместо него — явная типизация через
  дженерики/аннотацию типа там, где нужна проверка соответствия.
- Пропсы компонента — `<ComponentName>Props` (`LoginScreenProps`,
  `ButtonProps`).
- Тип ответа API — `<Module>Response` (`AuthResponse`), тип запроса —
  `<Module>Request` (`AuthRequest`). Единый вариант для всего проекта,
  `Dto`/`Payload` и подобные — не использовать.
- Для типов без предметного суффикса (`Props`/`Response`/`Request`) —
  суффикс `Type`: `StatusType`, `ThemeModeType`, `ModalNameType`. Если
  для типа уже есть свой предметный суффикс — используется он, не
  `Type` (не `LoginScreenPropsType`, а `LoginScreenProps`).
- Union-типы вместо enum везде, где возможно. `enum` в проекте не
  используется — окончательное решение.

  ```ts
  // ✅
  type StatusType = "idle" | "loading" | "error";

  // ❌
  enum Status {
    Idle,
    Loading,
    Error,
  }
  ```

## Переменные

- Имя должно отражать суть значения, не быть сокращением/одной буквой
  (кроме индексов в коротких циклах: `i`, `j`). Составные имена из
  нескольких слов camelCase приветствуются: `isLoading`,
  `selectedUserId`, `filteredOrdersList`.
- Булевые переменные — с префиксом `is`/`has`/`should`/`can`.
- Массивы/списки — во множественном числе или с суффиксом
  `List`/`Ids`/`Items` (`users`, `selectedIds`, `menuItems`).
- Не использовать общие бессмысленные имена (`data`, `temp`, `value`,
  `item`) там, где можно назвать конкретнее (`userProfile`,
  `selectedProduct`, `currentStep`).

## Константы

- Константы верхнего уровня, не относящиеся к конкретному модулю, либо
  неизменяемые значения-конфиги — `UPPER_SNAKE_CASE`
  (`MAX_RETRY_COUNT`, `DEFAULT_PAGE_SIZE`).
- Константы модуля в его `constants.ts`: `UPPER_SNAKE_CASE`, если это
  действительно неизменяемое конфигурационное значение; если это по
  сути дефолтный объект/пресет (дефолтные настройки формы, дефолтный
  конфиг) — camelCase. Других вариантов не вводить.
- **Повторяющееся значение — всегда в константу.** Если одно и то же
  "магическое" значение используется для сравнения/проверки более
  одного раза — даже в разных файлах одного модуля — выносить в
  именованную константу в `constants.ts` модуля (или в
  `core/constants/`, если значение нужно нескольким модулям), а не
  дублировать литерал. Уже второе использование одного и того же
  значения — повод вынести в константу, не дожидаясь третьего.

  ```ts
  // ❌ в двух разных файлах модуля:
  if (status === "123") { ... }
  // ...
  if (otherStatus === "123") { ... }

  // ✅ constants.ts:
  export const ARCHIVED_STATUS_CODE = "123";
  ```

## Комментарии и прочее

- Комментарии — только там, где код сам по себе не объясняет "почему"
  (бизнес-причина, обходной путь, ограничение библиотеки). Не
  комментировать очевидное.
- Запрещены комментарии "для вида": построчные пояснения к каждой
  строке, заголовки к самоочевидным блокам (`// получаем данные` над
  `fetchData()`), закомментированный неиспользуемый код. Если код
  нуждается в таком количестве комментариев — его стоит переписать
  понятнее, а не документировать построчно.
- Пометка "доработать позже" ставится только по явной просьбе
  пользователя: `// TODO: <текст на английском языке>` (например
  `// TODO: implement retry logic after API is ready`). Самостоятельно,
  без просьбы, такие пометки не ставить.
- Избегать магических чисел/строк — выносить в `constants.ts` модуля
  или `core/constants/`.
