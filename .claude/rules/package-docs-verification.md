# Не выдумывать API пакетов

Модель может путать версии API между мажорными релизами пакета, помнить
устаревший синтаксис или галлюцинировать несуществующие
параметры/методы, если отвечает по памяти вместо того, чтобы свериться
с реальной документацией. Поведение по умолчанию — противоположное:
**при любой неуверенности — идти и читать документацию, а не
додумывать.**

## Не выдумывать API

При написании или изменении кода, который использует внешний пакет
(`react-hook-form`, `zod`, `zustand`, `@emotion/react`,
`react-router-dom`, `vite`, ESLint/Prettier плагины, TypeScript, и
любой другой пакет из `package.json` проекта или новый, который
предстоит добавить) — нельзя полагаться только на память тренировочных
данных для конкретных имён методов, сигнатур функций, форматов
конфигов, названий опций и поведения по умолчанию. Если есть малейшая
неуверенность в точном API — это сигнал пойти и свериться с реальной
документацией/исходниками пакета, а не предполагать наиболее
вероятный вариант.

## Порядок проверки при сомнении в API конкретного пакета

1. Проверить фактически установленную версию пакета в `package.json` /
   `package-lock.json` (или аналоге), а не предполагать "последнюю"
   версию по памяти — поведение API может отличаться между мажорными
   версиями.
2. Проверить типы/декларации пакета локально
   (`node_modules/<package>/**/*.d.ts`, `README.md`, `CHANGELOG.md`
   внутри `node_modules/<package>/`) — это самый быстрый и точный
   источник правды именно для той версии, что реально стоит в проекте.
3. Если этого недостаточно — обратиться к официальной документации
   пакета в интернете (через доступный инструмент поиска/просмотра
   страниц), причём открывать документацию именно для той версии
   пакета, что используется в проекте, а не общую/последнюю, если они
   могут расходиться.
4. Если после этого всё ещё остаётся неопределённость — явно сказать
   об этом пользователю (какая часть API неясна и почему), а не
   выбирать правдоподобный вариант и выдавать его за проверенный факт.

## Предупреждать про новые версии пакетов

Если в процессе проверки выясняется, что у пакета, используемого в
проекте, вышла более новая мажорная версия, чем та, что зафиксирована в
`package.json` — сказать об этом пользователю отдельной репликой: какая
версия сейчас, какая новая мажорная доступна, вкратце — есть ли в ней
breaking changes, если это видно из документации/changelog. **Не
обновлять пакет самостоятельно** — это только информирование,
обновление версий — отдельное осознанное решение пользователя (в духе
[[safety-rules]]: не менять то, о чём явно не просили).

## Никогда не подавать выдумку как факт

Если не удалось найти достоверный ответ (документация недоступна,
инструмент поиска не сработал, пакет малоизвестный/приватный без
публичных доков) — прямо сказать "не удалось проверить X, вот что
известно из общих знаний, но это не проверено по актуальной
документации", а не писать код с уверенным тоном, будто это точно
правильный API.

## Баланс со скоростью ответа

Это правило имеет приоритет над скоростью ответа: лишняя проверка
документации, когда сомнения не было бы у опытного разработчика, не
нужна (не превращать в ритуал проверку тривиальных вещей вроде
`useState`), но там, где есть реальная неопределённость в специфике
конкретного пакета/версии — проверка обязательна, а не опциональна.
