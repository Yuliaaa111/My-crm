# Refactor

Приведение существующего кода в соответствие правилам из
`.claude/rules/`. Срабатывает только по явному вызову пользователя
(`/refactor ...`) — модель не предлагает и не запускает этот скилл сама.

## Определение режима по `$ARGUMENTS`

- Если явно указано `full`, "весь проект", "полный рефакторинг", "всё
  приложение" — режим **полного рефакторинга** (раздел 2).
- Иначе — режим **точечного рефакторинга** (раздел 1): `$ARGUMENTS`
  описывает конкретную задачу/модуль/файлы. Если аргумент не дан вообще
  — уточнить у пользователя, что именно рефакторить, не начинать
  наугад.

## Режим 1: точечный рефакторинг

1. Определить границы: конкретный модуль/файлы, указанные пользователем
   или следующие из контекста разговора.
2. Прочитать `.claude/rules/architecture.md`, `naming-conventions.md`,
   `code-conventions.md`, `imports-exports.md`.
3. Составить план по правилам `safety-rules.md`:
   `.claude/plans/refactor-<task-name>.md`, с чекбоксами по каждому
   найденному несоответствию, которое предполагается исправить.
   Дождаться подтверждения пользователя перед началом правок.
4. Выполнить рефакторинг строго в рамках согласованных границ, не
   расширяя объём на соседний код "заодно" без отдельного согласования.
5. После завершения — пройти финальную проверку из `safety-rules.md`
   (тайпчек, тесты по затронутому коду, самопроверка); для самой
   проверки можно переиспользовать логику скилла `code-review`, а не
   дублировать её здесь. Спросить пользователя, всё ли устраивает и
   можно ли удалить файл плана.

## Режим 2: полный рефакторинг всего приложения

Самая рискованная и объёмная операция во всём проекте.

1. **Сначала — только анализ, без единой правки кода.** Пройтись по
   всему `src/` и составить полный список несоответствий правилам,
   сгруппированный по модулям (`modules/<moduleName>`, `core/`, `app/`)
   — по тем же критериям, что использует скилл `code-review`
   (архитектура/слои MVVM, нейминг, `interface`/`any`/`satisfies`,
   экспорты, импорты, комментарии, дублирующиеся значения и т.п.).
2. Оформить это как план-чек-лист
   `.claude/plans/refactor-full-app.md`, где верхнеуровневые пункты —
   отдельные модули/области (не отдельные строки кода — при полном
   рефакторинге это будет слишком много пунктов), с кратким описанием,
   что именно не так в каждом модуле.
3. **Показать этот план пользователю и дождаться явного подтверждения
   объёма перед началом каких-либо правок.** При таком объёме работы
   пользователь может захотеть исключить часть модулей, отложить их
   или расставить приоритеты — нельзя молча взять весь список в работу.
4. После подтверждения — выполнять рефакторинг **батчами, по одному
   модулю/области за раз**, а не одним огромным изменением по всему
   репозиторию:
   - после каждого батча — отмечать соответствующий пункт в плане как
     `[x]`;
   - после каждого батча — прогонять тайпчек (и тесты, если они
     относятся к изменённому модулю), не дожидаясь завершения всего
     полного рефакторинга, чтобы ошибки не накапливались молча;
   - **не коммитить и не пушить самостоятельно** между батчами (см.
     `safety-rules.md`); если пользователь захочет закоммитить прогресс
     между батчами — это его решение и его прямой запрос, не инициатива
     агента.
5. Если в процессе полного рефакторинга обнаружится, что часть кода
   меняет поведение (не просто форму/структуру, а потенциально логику)
   — остановиться на этом месте, явно предупредить пользователя и
   уточнить, продолжать ли, вместо того чтобы менять поведение молча
   под видом рефакторинга.
6. По завершении всех батчей (или тех, что пользователь согласовал) —
   такая же финальная проверка, как в режиме 1, и вопрос про удаление
   файла плана.
