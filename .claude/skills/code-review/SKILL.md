# Code Review

Ревью кода проекта по правилам из `.claude/rules/`. Ничего не
исправляет самостоятельно — только выводит список замечаний.

## 1. Что ревьюить

- Если передан `$ARGUMENTS` (путь, имя ветки, диапазон коммитов) —
  ревьюить его.
- Если аргумента нет — ревьюить незакоммиченные изменения текущей
  ветки: `git diff` и `git diff --staged`.

## 2. Прочитать актуальные правила проекта

Перед ревью перечитать:

- `.claude/rules/architecture.md`
- `.claude/rules/naming-conventions.md`
- `.claude/rules/code-conventions.md`
- `.claude/rules/imports-exports.md`
- `.claude/rules/safety-rules.md`

## 3. Обязательный полный тайпчек

Запустить полную проверку типов по всему проекту (`npm run typecheck`,
если скрипт есть в `package.json`, иначе `tsc --noEmit` напрямую) —
именно по всему проекту, а не только по изменённым файлам, чтобы
поймать ошибки, которые правки могли вызвать в других местах. Все
ошибки типов — обязательные замечания, не "на усмотрение".

## 4. Тесты по затронутому коду

- Если папка тестов проекта (`src/tests/` или иная, если по факту
  используется) не пустая — запустить тесты, относящиеся к изменённому
  этой задачей коду (не обязательно весь набор целиком, если задача не
  про общепроектный рефакторинг).
- Если тестов на изменённый код нет — не ошибка, но упомянуть это в
  выводе.
- Если тестов в проекте нет вообще или папка пуста — пропустить шаг и
  явно указать в выводе, что автоматических тестов в проекте пока нет.

## 5. Критерии проверки

По каждому найденному замечанию — явно указать, к какому правилу оно
относится:

- **Слои MVVM и направление зависимостей** — `view → viewModel → model`,
  инкапсуляция модуля через `public/index.ts`, `core` не знает о
  `modules/` (кроме задокументированного исключения
  `useAppInitialization.ts`).
- **Расположение файлов** — `model/`, `viewModel/`, `view/screens/`,
  `view/components/`, `public/index.ts`.
- **Нейминг** файлов, папок, типов, функций, переменных, констант —
  `naming-conventions.md`, `code-conventions.md`.
- **Отсутствие `interface`, `any`, `satisfies`.**
- **Только именованные экспорты**, без `default`.
- **Порядок и группировка импортов** — пакеты → свои → стили.
- **Отсутствие мусорных комментариев**; `// TODO:` только там, где это
  было явно согласовано с пользователем.
- **Повторяющиеся "магические" значения**, которые стоило вынести в
  константу.
- **Формы** — через `react-hook-form` + `zod`, если в изменениях есть
  формы.
- **Стилизация** — через `stylesConfiguratorHook`/emotion, если в
  изменениях есть стили.
- **Отладочный вывод** — `console.log(...)`, `debugger`,
  закомментированные "на всякий случай" строки кода — пометить как
  **УДАЛИТЬ**.
- **Посторонние комментарии** — устаревшие, скопированные, не
  соответствующие текущей реализации, или просто мусорные — пометить
  как **УДАЛИТЬ**.
- **Потенциально небезопасная логика** — секреты/токены в коде или
  логах, отсутствие валидации пользовательского ввода там, где она
  нужна, широкие/отключённые проверки прав доступа,
  prototype pollution/XSS-подобные паттерны, `eval`-подобные
  конструкции и т.п. — пометить как **ПОПРАВИТЬ**, кратко объяснить
  риск.
- **Логически некорректный или подозрительный код** — несовпадение
  условия с ожидаемым поведением, забытый `return`/`await`,
  некорректная обработка ошибок, неверный порядок операций и т.п. —
  пометить как **ПОПРАВИТЬ**, кратко объяснить, почему это выглядит
  некорректно.

## 6. Формат вывода

Структурированный список замечаний:

```
Файл — правило/категория — в чём проблема — [УДАЛИТЬ / ПОПРАВИТЬ] — как исправить
```

Разделить по критичности:

- **Обязательно исправить** — всегда сюда попадают: ошибки тайпчека,
  упавшие тесты, отладочный вывод, потенциально небезопасная логика.
- **Стоит исправить.**
- **На усмотрение.**

Если замечаний нет — явно сказать, что код соответствует правилам,
тайпчек чистый и относящиеся тесты (если есть) проходят.

## 7. Не исправлять самостоятельно

Ревью только выводит список замечаний. Исправления вносятся отдельным
шагом и только после того, как пользователь подтвердит согласие с
замечаниями (правило из `safety-rules.md` про план и подтверждение
перед изменением кода).
